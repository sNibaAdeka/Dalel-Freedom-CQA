# Как измеряем качество Дәлел

## Что является эталоном

`eval/gold/silver.jsonl` (локальный файл, в публичный репозиторий не входит) — совпавшие ответы двух машинных разметок. Это удобный DEV-ориентир; согласие с ним не является точностью на человеческом эталоне. Трактовки критериев заданы в `cqa/prompts/guidance_v1.json`.

Независимый третий проход читает исходный диалог, официальный чек-лист и политику g6, не читая старые ответы. Его результат называется `silver-g6-candidate.jsonl`. Аудитор проверяет допустимые значения, полноту, версии, ссылки и дословность цитат. Изменения прежнего консенсуса, прежние разногласия и явно сомнительные ответы сохраняются в очереди разбора. Совпадение трёх моделей не заменяет человеческого решения.

Команда может зафиксировать машинный ориентир для DEV и запускать сравнения уже сейчас. Для независимой оценки качества нужны ответы экспертов или организаторов. Новый контрольный набор нельзя использовать для изменения промптов после просмотра его ответов. Отложенная выборка DEV (holdout) — это выборка для валидации модели и правил, а не тест: по ней выбирали между вариантами правил.

## Воспроизводимый аудит машинных разметок

```bash
python scripts/reference_audit.py \
  --data data/raw/dev_records.json \
  --pass-a data/processed/silver/pass_A \
  --pass-b data/processed/silver/pass_B \
  --review reports/reference-review/RU.jsonl reports/reference-review/KZ.jsonl reports/reference-review/EN.jsonl \
  --out reports/reference-audit
```

Без `--review` скрипт проверяет две исходные разметки. При наличии `--review` требуется полный набор ячеек. Неверная цитата, неизвестный диалог, пропущенная ячейка или несовпадающий хеш критерия останавливают сборку. Исходный Silver не перезаписывается. SHA-256 исходных файлов входят в отчёт.

Выходы: отчёт `reference_metrics.json`, таблица `agreement_by_criterion.csv`, полный кандидат и `adjudication-queue.jsonl`. Они содержат локальные данные и исключены из Git. Поле `needs_adjudication` нельзя игнорировать при описании зрелости эталона.

## Основные показатели

Это наш протокол измерения. Памятка организаторов задаёт формулу итогового балла и функциональный контроль, но не публикует порог точности или формулу лидерборда.

| Показатель | Как считаем | Что он проверяет |
|---|---|---|
| Exact match по ячейкам | Число точных совпадений / число ячеек эталона | Правильный ответ по каждому критерию; отсутствующий ответ модели считается ошибкой |
| Покрытие | Число полученных допустимых ответов / число ожидаемых | Ошибки выполнения не исчезают из знаменателя |
| По критериям, языкам, каналам | Exact match отдельно, с числом наблюдений | Общий процент не скрывает слабый C6, KZ или звонки |
| Macro exact match | Среднее exact match восьми критериев | Одинаковое значение критериев независимо от объёма |
| MAE итогового балла | Среднее абсолютное отклонение от эталонного итога, в пунктах из 100 | Практический размер ошибки; только полные сравнимые диалоги, их число отдельно |
| C8 precision / recall | TP/(TP+FP), TP/(TP+FN) | Ложные обвинения и пропущенные грубые нарушения; нулевой знаменатель → «не определено» |
| N/A | Матрица применимо / неприменимо + доля совпадений | Корректность основания для исключения веса |
| Доля ручной проверки | Число помеченных ответов / все ответы | Нагрузка на проверяющего; согласие голосов не калиброванная вероятность |
| Ссылки на доказательства | Действительные ID и дословные цитаты / все ссылки | Проверяемость источника; смысл цитаты требует отдельной оценки |
| Время и стоимость | Wall-clock на диалог, p50/p95; все вызовы, повторы и арбитр | Реальная цена выбранного режима; кэш и холодный запуск показываются отдельно |

Для шкальных C4/C6 дополнительно полезны MAE по исходной шкале и доля ошибок на одну/несколько ступеней. Они не заменяют exact match. Accuracy C8 без precision/recall малоинформативна при редких нарушениях. Общий κ по смешанным категориям также не заменяет κ каждого критерия.

Скрипт `eval_accuracy.py` уже считает согласие по критериям/языкам/каналам, матрицы ответов и MAE итогового балла. Остальные показатели протокола добавляются к отчёту явно; эта таблица не утверждает, что любой показатель уже измерен.

```bash
python scripts/eval_accuracy.py results/eval_runs/RUN.jsonl \
  --gold reports/reference-audit/silver-g6-candidate.jsonl
```

Такой отчёт подписывается «согласие модели с машинным кандидатом g6 на DEV». Для человеческого эталона подставляется согласованный человеческий JSONL. Публиковать одно число без названия набора, модели, режима, версии правил и знаменателя нельзя.

## Формула итогового балла по чек-листу

Для каждого применимого критерия: бинарный ответ даёт 0 или полный вес; шкала даёт `вес × оценка / максимум шкалы`. Затем:

`итог = round_half_up(100 × сумма набранных баллов / сумма применимых весов, 2)`.

При N/A вес исключается из знаменателя. Никакого округления промежуточных долей. C8 имеет нулевой вес и отдельный флаг; он не обнуляет итог. При отсутствии применимых критериев с весом итог не определён.

Контрольный пример: C1=yes, C2=N/A, C3=N/A, C4=15, C5=yes, C6=7, C7=yes, C8=no. Числитель `10 + 15 + 15 + 10.5 + 5 = 55.5`, знаменатель `65`, итог **85.38**.

## Заморозка и независимый контроль

1. Зафиксировать код, чек-лист, g6, конфигурацию модели и хеши данных/эталона.
2. Выполнить живой preflight. При недоступной модели записать сбой; не заменять её mock.
3. Обработать все выбранные диалоги, сохранив ошибки и пропуски, ответы, доказательства, время и usage.
4. Только после сохранения ответов присоединить эталон по `(conv_id, criterion_id)`.
5. Показать основной процент вместе с покрытием и подробными срезами. Разбирать ошибки уже после фиксации результата.
6. Проверить новый критерий через UI на замороженном коде; изменение правила и изменение веса — разные сценарии.

Пять звонков DEV — слишком мало для устойчивого вывода о качестве на звонках в целом. Аналогично, результат на новых контрольных диалогах следует представлять с числом ячеек и ограничением объёма выборки.
